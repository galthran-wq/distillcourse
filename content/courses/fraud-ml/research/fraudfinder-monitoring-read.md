## EXPLANATION PLAN
### The problem as the newcomer meets it
The module has produced three things a deployed model needs: a decision policy, an explanation per alert, and a weekly monitor with a life cycle. A real published pipeline — ten notebooks, a feature store, a training pipeline, an endpoint, a monitoring job, a serving handler — is the first chance to see whether a working system does what the theory says. It is a vendor's teaching artifact on synthetic data, which is exactly why it is readable end to end. The reader's task is an audit: for each gate and each monitor, find the module result it implements, and where it does not, say what would get through. The headline is in the opening: a deployment gate on accuracy > 0.95 at a 2% fraud rate is cleared by a model that never alerts.
Terms the newcomer does not yet have: pipeline DAG and a Condition gate, skew vs drift as the vendor uses them, request/response logging, sampling rate, explanation spec; all defined at first meeting from the notebook.

### Chain of sub-problems
1. **What the artifact is.** Answer: the data path (live transactions → stream → warehouse → batch and streaming features → one store), the training path (point-in-time training table → model → registry → endpoint), the serving path (message → store lookup → payload → score → log), and the monitoring job on the logs — drawn as the course's own system map, not the vendor's diagram. Because: the reader needs the components named once before the audit.
2. **The deployment gate.** The pipeline deploys iff accuracy > 0.95 (the first track) or iff average precision > 0.2 (the second). Obvious reading: both are gates. Why the first fails: at ≈2% fraud, predicting "genuine" for everything scores 0.98 — the module-2 arithmetic. Answer: the AP gate is the right kind (it is prevalence-aware; random AP equals the prevalence 0.02, so 0.2 is ten times random); the accuracy gate passes a constant model. Because: a gate is a threshold on a metric, and the metric must move when the ranking fails — accuracy does not.
3. **What the gate is measured on.** Obvious reading: a held-out set. The record: the notebook undersamples the majority class before the train/test split, so the test set is balanced; the pipeline splits 0.8/0.1/0.1 at random, with no delay block and no time order; the honesty note admits AUC 1.0 is an artefact of the synthetic data. Answer: the gate's number is computed on a sample the live stream will never resemble (balanced, random in time); the module-2 geometry — forward in time, delay block, natural prevalence — is what the gate should be computed on. Because: a threshold on a distorted sample is a threshold on nothing.
4. **The threshold choice.** The notebook sweeps thresholds 0.1 … 1.0, draws ten confusion matrices and picks argmax(tpr − fpr) — Youden's point — while its prose says the choice depends on the business cost of FP vs FN. Answer: Youden's point is the module-2 constant-cost rule with equal costs; the frontier of `score-to-action` is what the prose asks for. Because: the pipeline writes down the right question and answers a different one.
5. **The monitoring job.** The job needs a feature schema (for drift), a training-data sample (the pipeline's own train_table as the skew baseline) and an explanation spec (for attribution skew/drift); it samples 50% of requests, runs hourly, emails on breach; skew compares serving data to the training baseline, drift compares serving data over time; thresholds 0.5 (skew) and 0.05 (drift) per feature, with no stated reason; only 9 of the 25 payload features are listed. Answer read against the module: skew is the stability index between the development sample and now (step 1 of `model-risk-monitoring`), drift is the same index between two serving windows; the two thresholds are the textbook's 0.10 / 0.25 lights with no derivation; monitoring 9 of 25 features leaves 16 unwatched, among them the zero-filled minute features that are the known skew. Because: the job implements the label-free input check and nothing else — no performance backtest (it has no labels in the loop), no calibration pools.
6. **The explanation spec.** Sampled Shapley, top-5 attributions per prediction, returned by the service and logged. Read against `alert-explanations`: the investigator's object exists; the baseline is the training mean (not the customer's history); no reason code and no record of the action taken. Because: the pipeline produces attributions, not explanations for the three audiences.
7. **The serving handler.** It fills missing features with 0.0 (a cold customer becomes a "no activity" customer), always returns 204 so the message is never redelivered, and returns the score nowhere but the log; the feature contract is hand-copied in four places (two notebooks, the handler, the container's DATA_SCHEMA, the monitoring thresholds). Answer: training–serving skew is built in — the model trains on all-zero minute features and serves real ones — and no parity check exists; the handler's silence is a decision-zone policy with one zone. Because: parity is a property the module-3 lesson said must be checked by replay, and the pipeline never replays.
8. **The life cycle.** The pipeline has development, a gate, and deployment; no staging in parallel, no champion–challenger, no retirement; "upload model" picks the most recently updated endpoint; the hyperparameter loop reuses its index variable and picks the last model, not the best. Because: the textbook's five stages are what a bank's model-risk function would ask for, and the audit lists which are missing.
9. **The verdict as a table.** For each gate/monitor: the module result it implements, the result it omits, what gets through. The honest side: the series is about architecture, and says so; its data are synthetic; its defects are spot-the-bug material, not a judgment of the vendor. Forward: the AI Act's declared metrics and post-market monitoring plan would require the gate's metric to be stated and justified.

### Pitfalls and terms to define
- Skew and drift here are the vendor's words: skew = serving vs training baseline, drift = serving vs earlier serving. Map them to the module's index once and then use the module's names.
- The thresholds 0.5 and 0.05 are on the vendor's own distance statistic, not SSI; the lesson compares roles, not values.
- The series is a teaching artifact with a stated honesty note; the audit's tone is "what gets through", not "the vendor is wrong".
- Line numbers refer to the reader's flattened text; the writer quotes code short and names the notebook, never a line.
- The architecture diagram is the vendor's; the course draws its own map and uses the capture only as the artifact being read.
- No number from the synthetic data is treated as a fact about fraud (AUC 1.0).

## EXERCISE PLAN
1. [warm-up] At fraud rates 2%, 0.8% and 0.25%, compute the accuracy of the constant-genuine model and say at which rates the 0.95 gate passes it.
2. [boundary probe] Set the AP gate's threshold to the prevalence: show the random ranker passes it in expectation and derive the smallest threshold that excludes random at 95% confidence for a test set of 2,000 frauds.
3. [claim to refute] "Monitoring the nine most important features by importance covers the risk, since the other sixteen barely move the score." Refute: the sixteen include the minute features whose training values were constant zero — any serving value is skew, and importance measured on constant training columns is zero by construction.
4. [derivation skipped] Show that Youden's argmax(tpr − fpr) equals the Bayes-minimum-risk threshold only when C_FP·(1−π) = C_FN·π; compute the implied cost ratio at π = 0.02 and compare with C_a vs a mean amount of EUR 55.
5. [research-shaped] On the simulator, reproduce the skew the pipeline builds in: train on zero-filled minute features, serve real ones, and measure CP@100 and the stability index of the minute features; then run the parity replay of `real-time-scoring-architecture` and report the diff.
6. [mixed review, E3] The pipeline's monitoring has no labels in the loop: design the label join (feedbacks after δ) that would let it compute the bootstrap backtest of `model-risk-monitoring`, and state its clock.
7. [research-shaped] Estimate, from the monitoring job's 50% sampling and hourly schedule, the smallest input shift (as SSI) the job could detect within a day on the EDA's volume, and compare with a fraud wave that doubles the fraud rate for one hour.
8. FORWARD → `aml-transaction-monitoring-duty`: list every record the pipeline keeps per request (the serving_predict log row) and every record an investigator's decision would need; the reader finds the gap that the assessment record of the next module fills.

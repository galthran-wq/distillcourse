# Real-time scoring: latency budgets, feature stores and the rule layers — research brief

Lesson: `real-time-scoring-architecture` (module: system, type: core, status: planned). NEW — full re-synthesis, no draft exists, so no REVISION block.
Goal: Design the serving path of a fraud detector — latency budget, batch and streaming features from one store, rule layers around the model, daily retraining — and verify offline/online parity
Opening (verbatim, the lesson must start with it): A card authorisation must be answered within a few seconds and the model's share of that is under one. The features it needs — the card's last 30 days, the terminal's last week, the last 15 minutes — cannot be computed when the payment arrives. Where must they be computed, where stored, how kept identical to what the model was trained on, and what runs before and after the model in the same second?

## EXPLANATION PLAN
### The problem as the newcomer meets it
The reader has built features as of a timestamp (module 3) and a model selected on folds (module 4); both ran offline over a table. Now the payment is a message that arrives and must be answered. The newcomer does not have: a latency budget as a design constraint, "batch" vs "streaming" as two clocks, an online store vs an offline table, a parity check, a push subscription, a handler's acknowledgement contract. The opening's three windows (30 days, a week, 15 minutes) are the thread: each has a different cost to compute at request time.

### Chain of sub-problems
1. **What may run inside the authorisation?** — Obvious attempt: compute every feature from the raw history when the payment arrives. Why it fails: a 30-day aggregate over a card's rows is a scan of the history per request; a terminal's week is another; with ~400,000 payments a day the per-request recomputation exceeds the sub-second budget (the per-transaction latency warning from module 3's own source). Answer: split by clock — day-scale features computed in batch (SQL window functions over the warehouse, once a day), minute-scale features by a streaming job, and the request itself only looks up. Because: the budget leaves time for a key lookup and a model call, not for a scan.
2. **Where do the looked-up values live?** — Obvious attempt: the warehouse. Why it fails: the warehouse answers in seconds, not milliseconds, and its table is the training table, not "the latest value for card 4471 now". Answer: one feature store with two reads — offline, as-of a timestamp, for training rows; online, latest value by entity key, for scoring — fed by both the batch job and the streaming job. Because: if training and serving read different stores they drift apart (module 3's skew), and the point-in-time read the training set needs is the same log the online read takes its head from.
3. **How are minute-scale features computed without a scan?** — Answer: one sliding window of 60 minutes with a 1-minute period over the event stream; each event lands in many windows; TS_DIFF = window end − event time; 15- and 30-minute counts are conditional sums inside the 60-minute window; only "new records" (TS_DIFF ≤ period) are written, keyed by entity and window end. Because: one window gives three aggregates, and the new-records filter stops the same entity being written once per overlapping window.
4. **What exactly happens in the second?** — Answer: message → online lookup of the customer's and the terminal's features → a payload in the model's declared order → the score → the log row; the handler acknowledges every message so the queue never redelivers; rules run before the model (blocking: deny on an unsecured site) and after it (scoring rules add to the score; the decision policy of module 9 turns it into an action). Because: the queue's contract (redeliver until acknowledged) and the model's contract (a fixed feature order) are both part of the serving path.
5. **A customer with no history** — Obvious attempt: fill missing features with 0. Why it fails: zero activity is a real value — a cold customer scores like a dormant one. Answer: a missing-feature indicator, or a default from the training distribution, declared in the contract; the training table must have been built with the same rule. Because: the model never saw "missing"; it saw "zero".
6. **How do you know serving equals training?** — Obvious attempt: trust that both read the store. Why it fails: the reference pipeline trained on zero-filled minute features and served real ones — same store, different values — and its feature list is hand-copied in four places with the monitor watching 9 of 25. Answer: a parity check — replay a day's events through the serving path, log every payload, join to the batch features for the same (entity, timestamp), and diff; a contract declared once and imported everywhere. Because: parity is a property to test, not a consequence of architecture.
7. **When does the model change?** — Answer: daily, at the end of the day, retrained on the window and the feedbacks (module 7's cadence); scores from a graph propagation recomputed at midnight and used for the next day; a new model goes through the champion–challenger stage of module 9. Because: labels arrive by the day, and a model swapped mid-stream has no scored history to be judged on.

### Pitfalls and terms to define
- "Batch" and "streaming" name clocks (days vs minutes), not technologies; say so before any product word.
- "Online store" vs "offline store" vs "feature log": one log, two reads; define once.
- "Parity" vs module 3's "training–serving skew": skew is the condition, parity is the test; recall the term with a <Ref>.
- The reference pipeline is architecture illustration, not runnable-today code (stale pinned stack); the lesson reads its design, never recommends its versions.
- A push subscription's acknowledgement is not "the score was delivered" — the handler returns 204 even on failure; name that as a design defect.
- No vendor names in the body beyond "a cloud vendor's reference pipeline"; the components are generic (message queue, warehouse, store, endpoint).

## EXERCISE PLAN
1. Warm-up: with 400,000 payments a day and a 30-day window, estimate the rows scanned per request if the customer aggregate were computed live, and the per-request time at 10⁶ rows/s; compare with a 1 ms key lookup.
2. [claim to refute] "Both training and serving read the same feature store, so there can be no training–serving skew." Name the reference pipeline's zero-filled minute columns as the counterexample and the step that fails (same store, different write paths).
3. [boundary probe] Set the streaming window's period equal to its length (60 min / 60 min): what do the 15- and 30-minute aggregates become, and which events are written twice or never?
4. [derivation skipped] Show that a 60-minute window with a 1-minute period writes each entity at most once per minute under the new-records filter, and compute the write amplification without the filter.
5. [research-shaped] Build the parity check on the simulator: compute the 14 features in batch for one day, replay the day's rows through a serving function that reads an in-memory store, and diff; plant a zero-fill in the serving path and report which feature and which row the diff catches first.
6. [mixed review] A blocking rule "deny if the terminal risk over 30 days > 0.075" sits before the model: using <Ref> `point-in-time-features`, state which labels that risk may use at request time and what changes if the rule reads the feature from the batch store computed at midnight.
7. FORWARD → `label-maturation`: log every served payload for a day with its score; three weeks later join the investigators' dispositions and the disputes that arrived — the reader finds that most rows still have no label, and that the rows with labels are the ones the queue chose: the training set as of a date the next lesson assembles.

# generative-pretraining-and-tokenisation — ledger

NOTE (data): the BPE token counts are the writer's own, computed with tiktoken's
GPT-2 encoding (50,257 entries) on the running payment; the amount-bin edges are
from an illustrative lognormal stream (median €35, log-sd 1.25), labelled
illustrative in the lesson; token ids in tokens.svg and hash rows in hashing.svg
are illustrative.

**Problem.** How does a transaction row become tokens without losing the
amount's size or the gap, what should a model trained on them predict, and
what of that is useful for a task it never saw? Answer: one token per field
(text tokenisers waste the window and fragment numbers; at equal history text
scored nearly the same, so field tokens buy history); amounts as quantile bins + zero
bin, predicted as classes with a target smoothed over neighbouring bins; gap as
8·ln(1+Δ/8) plus calendar tokens; merchants via k hashed rows of a shared table,
row 0 for unseen, output tied to the table; key and value as separate vocabulary
entries summed into one position when SEVERAL fields carry text or one value list
recurs under many fields (one text field is fine per-field: nuFormer's field tokens
put the description beside them as BPE pieces) (not because events are of mixed kinds: per-field tokens name their field
and leave absent fields out, nothing padded).
Objectives: next-event prediction per field (+ past reconstruction for the far
past; both heads beat either on four public tasks), masked-field prediction in a
field/sequence hierarchy with the label column and static-field copy removed.
Downstream: the next-event distribution as a zero-label score; the last state as
columns, a feature not a detector (synthetic card AP 0.124 / 0.012 / 0.176).

## Explained
- Token, vocabulary, next-token prediction (Definition); untrained loss = ln|V|; byte-pair tokeniser (merge most frequent pair; 50,257 entries) — §Why not write the row as a sentence? / ### What a language model reads
- Running payment through BPE: 48 tokens with field names, 31 values-only; `184.00`/`1840.00`/`18.40`/`1,840.00` pieces table (18.40 shares digit pieces 18, 40 with 1840.00; 1,840.00 shares only `.` `00`); magnitude lost, same value split differently by preceding char (` 4` `471` vs `44` `71`), 7-digit merchant id → 3–4 meaningless pieces — ### One payment through a text tokeniser
- Per-field vocabulary (Definition): `hour=14` ≠ `mday=14`; marker token; running payment = 10 tokens (key image tokens.svg); currency token only when not home currency — ### A vocabulary per field
- Context window defined; attention cost grows with square of window; budget.svg: 48/31/10 tokens → 85/132/409 transactions per 4,096 window; published synthetic-card comparison ~39 vs ~12, 102 vs 315 in 4,092 — same ###
- Field tokens vs text at a bank's credit model: two possible reasons (better per-transaction reading vs more history) confounded in a fixed window → compare at equal transaction count. Setup: transformer pretrained by next-token prediction, trained with tabular features on 10M labelled rows, ROC-AUC on a later, non-overlapping test period; reference = field tokens, 1,024 window, 81 transactions; all figures relative change from it. Table: text (domain BPE; the field-token model also writes the description as BPE pieces) 1,024/31 −0.37%; field 352/28 −0.36%; text 662/20 −0.54%; field 224/18 −0.45%. KeyFact: at equal history nearly the same; field tokens buy history. Aside: general-text LLMs in the same 1,024 window hold fewer transactions (GPT-2-size 18, Qwen 0.6B/4B 24): −0.91%, −0.41%, −0.43% vs scratch −0.45% (field, 18) / −0.54% (text, 20); English did not make up for the history its tokeniser pushed out, and cost 3.7× / 9× training time — ### What the field tokens buy, measured
- Rounding to the euro (too many rare classes) and equal-width bins fail; scorecard's rejection of equal-frequency bins reversed (no label here; job = every class seen often) — §The amount / ### Bins that each hold the same share of payments
- Quantile binning (Definition): q−1 edges on nonzero pretraining amounts, amt_1..amt_q, amt_0 for exactly zero (a different event); q = 20 → 21 tokens; €184 → amt_19 (€173.69–273.53); top bin open-ended (€300 and €30,000 identical); finer grid trades tail resolution vs rarer classes. FigureSequence amount-1..3 + Task — same ###
- Plain CE ignores bin order; neighbourhood smoothing: 1−ε on true bin, ε spread over bins within r (one implementation r = 5; lesson uses r = 2). Example: A (near) and B (far) both 1.204 plain; smoothed 1.268 vs 1.597. In-body exercise C: 0.511 plain, 0.850 smoothed; minimum = target entropy 0.435 — ### What a plain bin target misses
- Aside: frequency features sin/cos(2^l π v), l < L, of standardised log amount → linear layer; €184 v = 1.328 vs €190 v = 1.353: l=0 near-equal, l=5 entirely different; L sensitive (no ablation number quoted) — end of amount §
- Positions count events, not time; a year ≈ 3×10^7 s vs a day 86,400 s (even grid wastes >99% of bins beyond a day); soft-log gap φ(Δ) = 8 ln(1+Δ/8) (Definition), token dt = floor, cap 140 (~10 years); linear below 8 s, +5.5 per doubling above; table 1 s 0.94 / 1 min 17.1 / 1 h 48.9 / 1 day 74.3 / 30 days 101.5 / 1 year 121.5; minute→hour +32 ≈ day→month +27; running gap 12,019 s → 58.5 → dt=58 (gap.svg) — §Time / ### A scale on which habits are evenly spaced
- Calendar tokens (hour, weekday, day of month) or cyclical sin/cos (Ref behavioural-profiles circle); transformer needs positions: Aside defines *position encoding* (sines/cosines of index i at several frequencies, added to each token's vector; same construction as the amount Aside's frequency features), then time-aware variants: learned w_p i + w_t t_i + b fed into those sinusoids and 64 ln(1 + t/60) rotary positions; measured effect deferred to reading-foundation-model-claims — ### The calendar, and time inside the model
- Row per merchant: 10^7 × 128 = 1.28B parameters, no row for new merchants — §Ten million merchants / ### A table row per merchant
- Hashed entity embedding (Definition): n ids seen in pretraining, S+1 rows, k hashes, each seen id's k rows computed once and stored in a fixed (untrained) lookup, vector = mean of k rows, row 0 = untrained zeros for ids missing from the lookup; n = 10^7, S = 10^5, k = 3 → 12.8M numbers; ~100 merchants per row per hash; k = 1 → ~100 share a vector exactly; k = 3 → ~10^-15 per pair, < 1 collision over 5×10^13 pairs; why row 0 and not hashing the new id: its 3 hashed rows would be trained by ~300 other merchants, a vector that looks learned and describes none; row 0 = the network lesson's "unknown" row, a signal (hashing.svg). KeyFact: collisions fall as S^-k while parameters grow ∝ S (uniqueness bought with hashes, not table size); every row carries gradients of n/S other merchants — ### Hashing into shared rows
- Weight tying: merchant score = state · merchant's input vector, no second 1.28B table; one payment network, relative to the same model with full table and untied output: hashing −22.6% peak memory, tying −73.8%; on an undisclosed internal anomaly-detection accuracy at an operating threshold, +1.9% and −0.6% relative. In-body exercise: n = 2M, d = 64, S = 50,000: 128M vs 3.2M, 40 per row at k = 1, untied head 128M — ### The output side
- Mixed streams (payment, transfer, login, support message): a per-field vocabulary already handles them — each token names its field, absent fields are left out, nothing padded; one public bank model writes profile/transaction/daily-geo events this way, ~8 tokens/event, event encoder bidirectional because field order carries no meaning — ### What a per-field vocabulary already handles
- Where it stops: (i) several text fields — too many values for a list; with one text field its BPE pieces can only come from it (nuFormer does this), with several the pieces (`metal plan` → `met` `al` `plan` under a bank's own BPE; GPT-2 gives `metal` ` plan`) from one shared tokeniser do not name their field; per-field answer = a subword vocabulary per text field; (ii) the same value list under many fields (bins under amount/fee/balance, ~250 countries under merchant/recipient/IP country) needs a copy per field, each learned from that field's events only — ### Where one token per field stops
- Key–value tokens (Definition): one value vocabulary shared by all fields, multi-piece value = one pair per piece with the same key, pair = one position, input = key vector + value vector (so a key costs no position); one bank: ~60 keys, ~28,000 values in one embedding table; percentile bins + zero bin, low-cardinality categoricals (MCC) one token, high-cardinality text BPE with [UNK]; within-field sinusoidal position encodings 0,1,2 (glossed via the time Aside), no order across fields; choice follows the fields, not the mix of events: several text fields or recurring value lists → key and value — ### When the key travels with the value (anchor `when-the-key-travels-with-the-value`, Ref'd by transaction-foundation-models)
- Next-event prediction (Definition): state h_t depends on no later event; head per field; loss = Σ_f −ln p̂_f(x_{t+1,f}); GRU or causal transformer (*causal* defined); token-by-token = same at finer grain; calendar of t+1 follows from gap → one payment-network model predicts gap, amount, merchant, MCC only — §Predicting the next event / ### The loss, field by field
- Example (next-event-1..3 sequence + Task): h_3 predicts 14:07 payment: 0.04/0.08/0.35/0.12 → 3.22+2.53+1.05+2.12 = 8.91; untrained ln141+ln21+ln600+ln10^7 = 30.51, merchant 16.12 of it; merchant term = largest share of what the loss can gain; MSE-on-log alternative needs hand weighting and predicts the mean of the log (recalls contrastive's 160). In-body exercise: next payment €12.40 bin 5, MCC 5814, merchant new to the card: 3.51+2.66+1.61+7.82 = 15.60 — same ###
- Every position graded: T events → T−1 predictions in one pass — ### Every position is graded
- Past reconstruction (Definition): head on (h_t, gap back) reconstructs x_{t−j}, weights exp(−Δ/λ) over last J events, total (1−α)L_next + αL_past; λ = 60 days: 1 week 0.89, 1 month 0.61, 6 months 0.05. Ablation SET UP here (four public tasks: churn 10k, age 50k, next-month spending 400k retail (squared error of log, lower better), credit default 1.5M; MLP→GRU 512 pretrained per dataset, frozen, average of states, 3-layer network on 80%, scored on 20%): NP/PR/both churn 0.814/0.833/0.845, age 0.630/0.542/0.642, spending 0.733/0.747/0.723, default 0.795/0.744/0.798; best α largest on churn (0.1 vs 0.001–0.005) (ablation.svg; setup paragraph precedes the figure). Pooling recalled from contrastive (avg +6% age, −0.5% churn): trait → average, recent change → last — stated ONLY here — ### What the next event cannot teach
- Why mask: next-event state sees only the past and is graded on t+1 only; a hole has context on both sides and any field can be asked; expectation raised that bidirectional = better representation (refuted in ### Which family). Masked-field prediction (Definition): window, [MASK], bidirectional, loss on hidden positions; field-level → sequence-level hierarchy (cheap attention); masking 15% tokens, 10% events, 10% fields (one field in every event); [UNK] positions out of the loss = input dropout (masked.svg) — §Hiding fields / ### Masking a window
- Two shortcuts (Ref contrastive shortcut): label column (fraud flag) removed before pretraining, because labels arrive late (Ref point-in-time label clock): live rows lack the flags of the current and recent events, so an embedding carrying them leaks and the downstream score measures the leak; same for any column computed from labels not yet arrived at the event's time (a terminal rate from today's labels) — NOT every label-derived column: the correctly built delayed rate is legitimate (Ex. 6); static field copied from neighbour → encode static fields once per window — ### Two shortcuts the masked task offers
- Which family: MBD generative 0.802 vs masked 0.762 vs supervised GRU 0.819 (Ref limits §the-ranking), one benchmark; generative state point-in-time by construction, advances per event; masked window must end at cut-off too — ### Which family
- Zero-label score: append marker + gap token to cut-off, probability of kind X; recalls limits' 0.79–0.92 and Markov 0.79–0.88; new: model predicts habits first, first-occurrence targets exclude them; zeroing customers who already had kind X lifts one target 0.72 → 0.91 — §What the trained model gives / ### The next-event distribution as a score
- State as columns: one state per event, each valid as of its own time, so last and average both point-in-time; reading follows the pooling rule of ### What the next event cannot teach (callback only; fraud is a recent change, so the synthetic-card run uses last); "now" event closes history at cut-off (silence counts); merchant-category vectors (average of states after transactions in a category) of a model pretrained on 5.1B transactions / 61M cardholders / 180 European issuers: Lufthansa → British Airways 0.23, Scandinavian 0.32; Hilton → Doubletree 0.19, Hampton 0.20; Fast food → Eating places 0.14, Convenience 0.26; no aggregate knows which merchants behave alike — ### The state as columns
- Synthetic card fraud measurement SET UP here (later lessons Ref ### On a fraud label: a feature, not a detector): 24M transactions, 20,000 simulated users, 0.12% rule-generated fraud; split by date 80/10/10; ~29M-parameter transformer, next-token on ~12 field tokens/transaction, vocab 6,251, last state = embedding; XGBoost on 1M balanced training sample, scored on 100k test rows at ~0.1%: 13 features AP 0.124 (ROC 0.9885), embedding 0.012 (0.8775), both 0.176 (0.9925); ~12× / ~120× / ~175× base rate, +42% AP; unknowns: which 13 features, whether embeddings read only earlier events, generator's rule vs real fraud → reading-foundation-model-claims (ap.svg). ## Notation
- u_i token at position i; |V| vocabulary size; ln|V| untrained loss
- q number of nonzero amount bins (q = 20 → amt_0..amt_20); ε smoothing mass; r neighbourhood (prose: "within two")
- v standardised log amount; L number of frequency pairs; l frequency index (Aside only)
- Δ gap in seconds (course's behavioural-profiles symbol); φ(Δ) = 8 ln(1+Δ/8); dt=⌊φ⌋ token, cap 140
- i event index; w_p, w_t, b, t_i (Aside only, position encoding and time positions)
- n ids, S shared rows (+ row 0), k hash functions h_1..h_k; d written as numbers (128, 64)
- x_t event t, h_t state after event t, f field, p̂_f head probability; Δ_{t,t−j} gap back to event t−j; J past events; λ decay length; α past-reconstruction weight
- Token names: [EVT], [MASK], [UNK], dt=, hour=, wday=, mday=, amt_k, ch=, mcc=, cty=

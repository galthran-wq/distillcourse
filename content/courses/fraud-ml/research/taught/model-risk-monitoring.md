# model-risk-monitoring — ledger

NOTE (data): every simulator number is this lesson's own run (scripts in the writer's session scratchpad, not committed; the revision's merged-pool HL numbers from mrm/hlmerge.py and mrm/hl3.py on the same main.pkl): the lab's rewrite of the handbook generator (`cost-aware-evaluation-lab/solution.py`'s `simulate`, numpy seed 0, 5,000 customers, 10,000 terminals, 133 days) with two optional planted changes from day 84; fifteen baseline features with the 7-day label lag; sklearn HistGradientBoosting (max_depth 3, 100 iterations, learning rate 0.05, min_samples_leaf 100, seed 0) trained on days 35–41 with known cards removed (55,103 payments, 344 frauds); development week days 42–48; twelve monitored weeks from days 49, 56, …, 126. Known-card removal = a fraud on the card in [d − δ − 28, d − δ − 1] (28-day window, because the simulator keeps customer ids after the bank would reissue the card); detected cards removed for 28 days; CP@100 restarted per week. Undersampled variant: same learner on all frauds + genuine kept at 2% (β = 0.0212, 1,503 rows). The product stream is a separate draw from the same rules (its own model on its own days 35–41, 54,642 / 371); the method stream is the unchanged stream until day 84 (same model). Bootstrap: 1,000 draws, units = cards, pooled. Reference spread for backtests = first five monitored weeks (days 49–83, labelled by day 90). Prequential folds = deployed recipe trained on a week, validated on the next, validating days 21–27 … 42–48 (the two folds trained on days 0–6 and 7–13 dropped: inputs over histories only days long, AP 0.29 and 0.45; the kept folds still run on partly filled 30-day windows, e.g. days 14–20, unlike the deployed model trained from day 35 — stated in the lesson as one more reason the fold spread understates the live one; mrm/b_folds.py, folds.pkl). Daily missed share = 1 − TP/γ per day with known- and detected-card removal, CUSUM v 0.5 h 5 on z with level/spread from days 42–83. Staging: paired card-level bootstrap (300 draws per week) of CP@100 difference, challenger = same learner trained on days 35–48. Stability-index bins = development deciles (ties leave shares a few thousandths off 0.1); empty bins floored at 1e-4. The Baesens textbook tables (0.0605 total; 'Years client' 0.304) were NOT used in the body; the worked index is the course's own product-stream week 112.

**Problem.** Which numbers to compute weekly on a deployed detector to tell whether inputs moved, ranking still works, probabilities still hold, and what happens at red. Answer: three questions on different clocks; stability index (= IV between two periods) on score and every input against the development week (label-free, same day; blind to fraud-only changes, so also on confirmed frauds δ late, read beside genuine rows); performance backtest on the latest labelled week as z against the spread of ordinary live weeks, accumulated by CUSUM (fixed % rule fires on ordinary weeks; development folds give a floor and false-alarm; card-level bootstrap where no run of weeks exists, and paired for champion vs challenger); calibration pools with binomial test and Hosmer–Lemeshow, over-rejecting because frauds come in clumps → early warning; lights → actions table; life cycle (development, testing, staging champion–challenger on complete labels, production, retirement), changeover modes, nightly retrain as an approved procedure; monitoring plan and documentation test; legal gates.

- SI = information value with the two periods as the two classes (Ref scorecards-woe); age table IV 0.65 read as a week far into red; 0.25 ≈ upper-medium IV; reading flips (selection wants large, monitoring fears it); binning fixed at development; symmetric; = KL(o‖e) + KL(e‖o) (derived in exercise) — ### The index is the information value between two periods
- Two references: development week (how far since approval, decides) vs previous week (dates the change); card 30-day count 0.03, 0.21, 0.34, 0.47, 0.56 vs development, 0.04, 0.08, 0.02, 0.01, 0.01 week-on-week; KeyFact: windows turn a sudden change in payments into an incremental one in features (Ref concept-drift how-the-change-arrives-in-time) — ### Two references

- Red input = change in p(x) (virtual drift if p(y|x) holds; Ref concept-drift naming-the-three-parts), not proof of harm, a question for the labels (product AP 0.61 → 0.53, under 2 weekly sd; no forward verdict given here); second cause: training–serving skew (Ref point-in-time-features one-definition-for-training-and-serving), one input jumps the day code deploys, zero-filled column = all in one bin; cheapest pipeline test — ### What a red input means

- (Order: HL section precedes clumps.) - Retraining is incomplete both ways; lights → action table (pipeline fix / watch / recalibrate / retrain challenger / retrain + index says on what) read as a decision table: read with each light red / not red (yellow, orange = not red: look, not act): gap (all green) and three overlaps (one input red overnight also matches row 2, 3 or 5 per the other lights), priority pipeline first (a broken input can move ranking or probabilities; a challenger fed it inherits the fault) (Ref score-to-action completeness-and-consistency-checked-by-a-program) — §What happens at red / ### From a light to an action
- Five stages (figure lifecycle.svg): development (records metric spread = provisional backtest reference), testing (latency within the deadline under load, missing/extreme inputs, dummy fraud cases), staging (challenger beside champion on the same live payments, only champion acts), production, retirement (repository; benchmark; recomputing an old decision from the record's model version, Ref alert-explanations supervisor record) — ### Five stages
- Champion–challenger trap: fast labels exist only for the champion's alerts (Ref alert-feedback-selection-bias); compare only on complete labels δ after each week; staging = labelled weeks needed + δ. - Changeover: direct, phased (segment by segment; noisier lights), parallel (weighted score shifting over months = a third model whose calibration pools are checked) — ### Changing over
- Nightly retrain as an approved procedure: features, algorithm, search, window, automated gates fixed once; each nightly model passes testing checks, score index vs champion, backtest within the reference spread, else yesterday's stays; anything outside = new model through all five stages — ### Retraining every night is a change agreed in advance
- Monitoring plan: per number computation, reference, thresholds, action per colour, who decides; extra weekly quantities: surcharge λ, override rates per cell, per-group FP rates (Ref score-to-action), attribution-mix index (Ref alert-explanations exercises), grounding-check failure and edit rates (Ref llms-in-the-investigation-queue); model design questions (when/by whom, perimeter, inputs/output, strengths/weaknesses, data and time span, sampling, human judgement); documentation test (a newly hired team continues from documents alone) — §Written down / ### What the plan holds
- Legal gates (opened as: two gates the bank may not set for itself, and a third — AI Act — only where the model is high-risk; the lesson's fraud detector is carved out), one line each: PSD2 RTS Art. 3(2) (yearly audit of TRA methodology, model, fraud rates; external first year and every 3 years), Art. 19 (fraud value over total value of ALL remote payments of the type, exempted and SCA-authenticated alike, rolling 90 days, at or below a reference rate; read as a backtest in money of how the model routed them (it includes authenticated payments and exemptions the model did not decide), against a legal line, not the model's predictions); AMLR Art. 10(1) (risk assessment before new products or new/developing technologies used with new or existing products: a new payment product is assessed before going live = part of the testing gate; a model counts only on a reading, flagged as such: a technology new to the bank (first ML model, an LLM drafting narratives) arguably, a retrained challenger of the same kind not); AI Act Art. 72 (post-market monitoring plan, high-risk only), Art. 43(4) (pre-determined changes not a substantial modification), fraud detection carved out of the credit-scoring high-risk line — ### Where the law fixes the gates

## Notation
- e_i expected (development) share, o_i observed share of bin i, B bins; SI stability index
- g_i/N_g, f_i/N_f genuine/fraud shares (from scorecards-woe) in the IV identity; KL(a‖b) in an exercise
- BS Brier score; p_j, y_j
- Pool: n (or n_i) payments, P̂ (P̂_i) mean predicted probability, θ (θ_i) frauds, p* critical rate, z_α standard normal quantile, K pools, χ²_HL Hosmer–Lemeshow statistic
- m clump size (exercise: Σm_j²/Σm_j for unequal clumps); M a generic metric in the bootstrap
- δ = 7, k = 100, π base rate, c change day (course symbols); λ surcharge (score-to-action)

Training–serving skew is a difference between the features a model was trained on and the features it is served — and it is invisible to every offline metric, because the offline pipeline is the one that is wrong.

Module 3's manufacturing line is three stations long: <Ref lesson="labels-and-feedback-loops">labels</Ref> with their sources priced, <Ref lesson="data-leakage-and-splitting">splits</Ref> that keep the offline metric honest, and <Ref lesson="features-at-scale">features</Ref> built to survive production. That last lesson closed on the open wound: every transform now runs in two places, the training pipeline and the serving path, and nothing yet guarantees the two computations agree; the Netflix timestamp already showed the two sides disagreeing by construction. This lesson names the gap, measures it, and repairs it; what the repairs still need, an automated watchdog, is the module's <Ref lesson="data-validation">final lesson</Ref>.

The route: a four-month postmortem and the mechanism of its silence; the boundary between skew and drift; skew decomposed into three measurable gaps; three repair architectures, each honestly costed; and the one case where training and serving inputs differ on purpose.

## One transform, two implementations: the Spotify postmortem

The wound — one transform in two places, nothing holding the copies equal — has a canonical postmortem, and it starts at a recommendation shelf. Spotify's Podcast Model ranks podcasts for the "Shows you might like" shelf. The training pipeline reads raw listening data from the warehouse, transforms it into features, and trains; serving is a recommendation service on different infrastructure, owned by a different team, which computes the same features from live data and calls the model. One logical transform, two implementations; the serving implementation differed from the training one by a few lines of code.

Nothing failed. Both implementations were valid programs producing plausible feature values: no exception, no crash, no alert. The model simply received inputs drawn from a slightly different distribution than the one it had learned, and its recommendations degraded for **four months** before the team detected it.

### The mechanism of silence

The silence has a mechanism. Every offline metric (the validation AUC, the holdout precision, the pre-launch evaluation) is computed on features produced by the *offline* transform. When the two implementations disagree, the offline pipeline is the wrong one of the pair: the metric that certifies the model is computed by the pipeline the bug lives in. <Ref lesson="feature-platform">The feature platform's second seam</Ref> stated this for post-fetch transforms; the Spotify bug is the same blindness at full pipeline width, and it is the production-scale version of the two-teams arrival-time bug <Ref lesson="batch-and-stream-processing" id="two-pipelines-one-bug">the stream-processing lesson</Ref> recorded: a batch dataframe on one side, a streaming window on the other, a team on each.

### The fix: one implementation, a feature log, a comparator

The fix Spotify shipped has three parts, and they preview the rest of this lesson: implement the transform once, in Java, so the serving path runs it natively; log the already-transformed features at serving time and assemble future training sets from the log; and compare training and serving feature distributions on a schedule with [TensorFlow Data Validation](https://www.tensorflow.org/tfx/guide/tfdv), alerting when the Chebyshev distance between them moves. Logging happens at the serving stage rather than in upstream services deliberately: the upstream transforms are owned by other teams, and the ML team must own the point where its own training data is captured.

<KeyFact>
The first honest signal of training–serving skew is a live business number sagging for unattributable reasons — a signal owned by another team, denominated in revenue, and pointing at nothing. Spotify's took four months to trace back to the transform.
</KeyFact>

## Skew is not drift: the boundary module 6 depends on

Repairing the right disease requires separating two that share a symptom. The production-systems literature lists three causes under the name training–serving skew: a discrepancy between how the training and serving pipelines handle data; a change in the data between training time and serving time; and a feedback loop between the model and its own inputs. This course splits them.

*Skew* is the first cause: your two computations disagree about the same world, an engineering defect on your side of the boundary. *Drift* is the second: the computations agree and the world moved. Feedback loops, the third, are <Ref lesson="labels-and-feedback-loops">the labeling lesson's</Ref> loops now running against the model's own inputs in production. The symptom is identical (live performance below offline) but the repairs are disjoint: skew is fixed by architecture, drift by data and retraining, loops by exploration. <Ref lesson="failures-and-drift">Module 6</Ref> opens by taking drift and loops as its subject, and it can only do so because this lesson takes skew off the table.

### The joined-table case: the pipeline test decides

The line is not always clean, and one classic sits astride it. A model joins document features (comment count, click total) from a table, at training time and again at serving time. No code differs. But the table's contents change between the training run and the serving moment, so the same document carries different feature values on the two sides. It behaves like drift (data moved) yet it yields to skew's repairs: log the feature values serving actually used, or snapshot the table so both sides read one version. The operational test is not "did the data change" but "could engineering have pinned the value": if yes, treat it as skew.

<Remark title="a mismatch that is not skew">
An augmented-reality startup with its office in St. Petersburg, a Baltic-coast city with about 1,600 sunny hours a year, collected and tested its computer-vision training data locally, through a cloudy Russian winter. Its lead investors demoed the prerelease build in Cyprus, a Mediterranean island with 3,400 sunny hours, and the vision component collapsed under full sun. By the pipeline test this is not skew: no two implementations disagreed. The training set failed to represent the serving environment from day zero: a distribution mismatch wearing skew's symptom. The discipline when live falls below offline: run the pipeline test first, because it is the one question with a definite answer.
</Remark>

## Measure before repairing: the three gaps

A repair chosen before the loss is located is a guess. The instrument is one model evaluated four times: on its **training set**; on the **holdout** split; on **next-day data** (examples from after the training cutoff, per the rule that a model trained on data through January 5th is tested on January 6th and after); and on **live traffic**, a sampled slice scored with the features the serving path actually computed. Rules of ML #37 reads the three gaps between the four numbers as three different diseases.

| gap | between | cause family | expected size | repair lever |
|---|---|---|---|---|
| 1 | train → holdout | overfitting | always &gt; 0, not always bad | capacity, regularization |

### Gaps 1 and 2 are statistics; gap 3 is an equality

Gap 1 is the familiar one and carries no production news: it exists in every fitted model, and shrinking it to zero usually means underfitting. Gap 2 is the price of time: features whose predictive value decays make next-day performance drop below holdout, and a large gap 2 is a portfolio finding (some feature is aging fast) answered by retraining cadence or by replacing the feature, not by pipeline work.

Gap 3 is different in kind, not merely in cause: it is testable as an equality on a **single example**. Score one example through the training pipeline and score the same example through the serving path; a correct system returns bit-identical results. Gaps 1 and 2 are statistical estimates; gap 3 has a deterministic test that either passes or names an engineering error. The Spotify bug lived entirely in gap 3, and the single-example test would have found it on day one.

### The Netflix timestamp, classified

The decomposition also settles the module's outstanding case. <Ref lesson="features-at-scale" id="the-clock-a-feature-that-cannot-overlap">The Netflix timestamp feature</Ref> (raw play timestamps plus the current clock, worth an offline lift on the order of tens of percent) puts its serving value strictly outside the training range on every request. It does not sit in gap 3: both sides compute the feature with the same code, and the single-example test passes exactly. It is gap 2 in its most extreme form, a feature time-sensitive by construction, whose holdout-to-next-day drop grows with every hour since the training cutoff. The prescription follows the classification: no transform architecture helps, a tight retraining cadence bounds the damage, and next-day replay measures it. Misclassify it as gap 3 and a team spends a quarter unifying pipelines that already agree.

<KeyFact>
The fourth evaluation is not free: gap 3 exists only between next-day replay and live traffic scored with the features serving actually computed — so a team with no serving-feature log cannot measure its skew at all, only infer it from a sagging business metric. The instrument presupposes the first repair's machinery, run at sampling scale.
</KeyFact>

## Repair 1: log what serving saw

The first architecture removes the disagreement by removing one of the disagreeing parties. Serving computes the features anyway, for every real request; Rule #29 says to treat that computation as the *only* one: append each request's transformed feature vector to a log, and assemble the next training set from the log joined with labels as they arrive. The training pipeline stops transforming raw data entirely. There is nothing left to diverge, so the gap-3 test passes by construction: training features are serving features, byte for byte. YouTube's home-page team made exactly this switch and reported significant quality improvements along with a reduction in code complexity: one implementation is also less code.

Two more properties arrive free. A feature logged at request time is, by construction, the value *as of that request*: the point-in-time discipline repair 3 will need machinery for costs this architecture nothing. And the training distribution becomes exactly the served population: the model stops training on warehouse traffic it will never see (the bot-filter exercise below works out when that correction helps and when it bites back).

### What log-and-wait costs

The costs are real and the first one is the commonly missed one:

- **New features wait.** A feature must be computed and logged at serving (live or in shadow) before any training set contains it, so adding one costs a full training window of waiting. A team that adopts log-and-wait without noticing this has silently capped its iteration speed at the logging horizon.
- **Storage.** Full feature vectors per request add up; the standard answer is to log a fraction of traffic.
- **Consistency is not correctness.** One buggy implementation is now wrong on both sides, consistently, and gap 3 will never see it.

<Remark title="sampling with importance weights (Rule #30)">
When storage forces sampling, do not keep files 1–12 and drop files 13–99. Sample each example with probability $p$ and give the kept ones weight $1/p$: logged at 30%, an example carries weight $10/3$. Importance weighting preserves the calibration properties the ranking modules will depend on; arbitrary dropping quietly reshapes the distribution the log exists to capture.
</Remark>

Where full logging is impossible, Rule #32 states the fallback: share code between the two pipelines wherever the batch/online difference allows. Its corollary has the sharpest edge: do not put training and serving in different programming languages, because that makes sharing nearly impossible. Spotify's four months began life as a Python/Java pair.

## Repair 2: bake the transform into the artifact

The second architecture attacks the interface. A model trained on transformed features exports a prediction signature that *demands* transformed features, which forces every caller to reimplement the transform. The Transform design pattern's canonical example is a bicycle-ride-duration model trained on three features (station name, day of week, hour of day) computed from two inputs, station name and timestamp. At prediction time the caller must send `dayofweek` as `'3'`, and whether that means Tuesday or Wednesday depends on which library's week convention the training pipeline used. The transform's private details have leaked into every client, and each client is a fresh chance to reintroduce Spotify's few divergent lines.

The pattern keeps three things separate: *inputs*, what the caller has; *features*, what the model computes on; and *transforms*, the mapping between them. It then captures the transforms **inside the artifact**, so the model's public interface accepts raw inputs. One implementation exists; it ships with the weights; the serving path cannot diverge from it because the serving path executes it.

### Instance-level, full-pass, and the analyze phase

One distinction decides how much of a transform can ride in the artifact, recalled from <Ref lesson="features-at-scale">the feature lesson</Ref>'s statistics discussion:

- An *instance-level transform* (a feature cross, an hour-of-day extraction, a hash) maps one row using nothing but that row. It can live directly as a layer of the model graph.
- A *full-pass transform* (scaling by mean and variance, building a vocabulary) needs statistics over the whole dataset, and serving sees one request at a time: the statistics cannot be recomputed there.

The resolution, in the shape `tf.transform` implements: an *analyze phase* runs over the training data once and computes the statistics; the emitted *transform graph* contains the instance-level logic with those statistics frozen in as constants; and the graph is prepended to the exported model, so serving applies mean and variance it could never compute. Training reads the pre-transformed data, so the transform also stops re-running every epoch. The pattern is what matters here, not the library; the platform that operationalizes it is <Ref lesson="inside-tfx">module 4's TFX lesson</Ref>.

### The leakage lesson's scaler, given its name

This is <Ref lesson="data-leakage-and-splitting">the leakage lesson's</Ref> scaler-artifact answer, generalized. That lesson established that $\mu_{\text{train}}$ and $\sigma_{\text{train}}$ must ship with the weights; the Transform pattern is the shipping mechanism with the discipline built in: the statistics are *part of the model*, not a config file beside it. The feature platform's post-fetch fork, where serving normalized by months-old config constants, is precisely what the pattern makes unrepresentable.

Its costs: an analyze pass before training; artifact weight, since vocabularies and lookup tables ride inside the model; framework coupling (the transform must be expressible in the serving runtime's operations, so a stack whose service and model frameworks differ may simply be unable to execute the graph); and training-only transforms such as data augmentation stay outside the pattern, since serving must never apply them.

## Repair 3: the feature store as single source, and the as-of join

The third architecture is already built. <Ref lesson="feature-platform">The feature-platform lesson</Ref> assembled it: each feature declared once, computed once at ingestion, materialized to an offline store for training and an online store for serving. That lesson closed by conceding that storage consistency is not transform consistency; the concession can now be given an exact scope. The store eliminates *duplicated feature pipelines*: the transform that produced a stored value ran exactly once, so no Spotify-style pair of implementations exists for it. What it leaves open is everything after the fetch, which is repair 2's territory, and end-to-end certification of what the model actually received, which is repair 1's. The three repairs compose; they do not compete.

The store-side guarantee this lesson must add is temporal. A training set is assembled by joining feature values onto label rows, and the join has one correct form.

<Example title="the as-of join, on six rows">
Label row: customer 42, label time $T = $ Mar 12, label = "placed an order within 7 days after $T$". Feature history for `spend_90d`, customer 42, as the offline store holds it:

| valid from | spend_90d |
|---|---|
| Jan 05 | 118 |
| Feb 10 | 233 |
| **Mar 09** | **296** |
| Mar 20 | 341 |
| Apr 02 | 402 |

The *as-of join* attaches the latest value whose validity begins at or before $T$: Mar 09's 296. The naive join (`JOIN ON customer_id` against the current table) attaches 402, a value computed over a window that *contains the label window* (Mar 12–19) and everything since. The feature has absorbed the outcome it exists to predict: this is <Ref lesson="data-leakage-and-splitting">temporal leakage</Ref>, reached through the feature store, and the offline metric it inflates is exactly as confident and exactly as wrong as the leakage lesson promised.
</Example>

### Point-in-time correctness: a training-side guarantee

*Point-in-time correctness* is the store-side guarantee that every training join is the as-of kind: the contract `get_batch_features` documented in the platform lesson, now with its reason attached. Serving needs no such machinery: a request reads the online store's current value, which at that moment is the as-of-now value, legitimately. The asymmetry is worth stating: the naive join is wrong only on the **training side**, which is why the bug inflates offline metrics and then vanishes into a gap-3 reading when live traffic, which cannot time-travel, fails to reproduce the inflated signal.

### Choosing among the three

Choosing is a matter of constraint, not taste. Log-and-wait fits when serving already computes the features and the team can wait a training window; transform-in-model fits when the transforms are instance-level (or full-pass with an analyze phase) and one framework spans the stack; the feature store fits when features are shared across models and teams and precomputed on their own cadences. A mature stack typically runs all three at once: the store supplying values, the artifact carrying post-fetch transforms, the serving log certifying end to end and becoming the next training set.

<KeyFact>
Every repair in this lesson buys consistency, not correctness: it guarantees one implementation, not a correct one. The uniformly wrong transform is the entry point no architecture closes; it is what the next lesson's schema and distribution checks exist for.
</KeyFact>

## Skew by design: the positional feature

Everything so far treats any train/serve input difference as a defect. From that, one would expect the discipline to be total: every feature identical on both sides, always. Rule #36 maintains a deliberate exception, and it is the exception that proves the rules are about *control*, not sameness.

Position bias: an item shown in the first slot is clicked more *because of the slot*, and a model trained naively on click logs learns that its own past ranking decisions are relevance. The repair is to give the model a `position` feature at training, so the click's positional component has somewhere to go other than into the document's weights, and then to withhold it at serving, because candidates are scored *before any order exists*: there is no true position to send. Every serving request carries the same constant default. Training inputs and serving inputs differ on purpose, permanently.

<Figure
  src="./figures/positional-feature.svg"
  alt="Two panels. Left, training rows: a table of examples whose position column is filled with the real slots 1, 2, 3, 5 shown in blue. Right, a serving request: candidate rows all carrying position equals 1 as a constant default in amber, annotated that candidates are scored before any order exists. A band underneath states the additive rule: score equals f of the document features plus g of position, with position never crossed with document features."
  caption="Managed skew: position is real at training, constant at serving, and confined to an additive term the serving path can hold fixed."
/>

### Confinement: additive, never crossed

What makes this managed rather than pathological is confinement. The rule keeps the positional part of the model **separate and additive**, score $= f(\text{document features}) + g(\text{position})$, and never crosses position with any document feature. The asymmetry then lives inside one term, $g$, that serving holds constant; the moment position leaks into an interaction, withholding it at serving changes the document scores themselves, and the deliberate difference becomes ordinary skew. Ranking's deeper position-bias machinery (propensity weighting, exploration) belongs to <Ref lesson="ranking-and-ctr">module 7's ranking lesson</Ref>; what this module owes it is only the transform discipline above.

### The exception breaks the naive monitor

A comparator that checks "every training feature appears in serving requests" will page on `position` forever: the feature is *supposed* to exist in training and not at serving, and saying so requires a schema that can state presence per environment. That is precisely the machinery of the next lesson, and the last exercise below lands on it.

What is established: skew is the pipeline disagreement, distinct from drift by the pipeline test; it decomposes into three gaps of which only the third should be zero, giving a deterministic single-example test; three composable architectures close it (logging serving-time features, baking transforms into the artifact, serving from a feature store with as-of joins); and one input difference, position, is maintained deliberately inside an additive term. The repairs share a dependency this lesson has only gestured at: a machine that watches feature presence, types, and distributions without a human in the loop. <Ref lesson="data-validation">The next lesson</Ref> builds that watchdog (schemas, statistics, drift comparators) and reproduces the reasoning behind the Google Play fix it bought a measured +2% install rate with.

Warehouse training: the base click rate the model calibrates to is $0.75 \times 0.08 + 0.25 \times 0.40 = 0.16$. The population it serves has base rate $0.08$: predictions are calibrated to a mixture that includes traffic the model will never score, overestimating click propensity roughly twofold on every real request (and worse, the bot segment's feature–label relationships contaminate the learned weights).

Log-and-wait training: the log contains exactly the requests that passed the bot filter, so the training distribution *is* the served population: base rate $0.08$, human-only feature relationships. The offline/online mismatch this removes was never drift or pipeline skew; it was training on a population the system does not serve, and logging corrects it automatically.

The backfire condition: the log is filtered by *the current model's own decisions*. When serving-time selection depends on predictions — a recommender only logs impressions for items it chose to show — the log stops being "the served population" and becomes "what the incumbent model liked," and training on it entrenches those choices: a degenerate feedback loop, the third cause in the skew/drift/loop taxonomy. The distinction that decides: a bot filter selects independently of the model's scores; a ranker's item selection does not.
</Solution>
</Exercise>

<Exercise>
Choose the repair architecture for each stack below, and name the property each choice forfeits:

(a) Training runs in Python against the warehouse; serving is a Scala service owned by another team. The features feed this one model only, which retrains monthly, and the team can tolerate a month's wait before a new feature is trainable.

(b) Fifty customer features are consumed by four models across three teams, each feature precomputed on its own refresh cadence.

(c) One TensorFlow stack spans training and serving; the transforms are feature crosses plus mean–variance scaling; the team ships a new feature most weeks and cannot wait a training window for logs to accumulate.

<Solution>
(a) **Log-and-wait.** The Python/Scala split is Rule #32's two-languages corollary in the flesh: code sharing is nearly impossible, and transform-in-model is blocked by framework coupling (the graph must be expressible in the serving runtime, and the serving runtime is another team's Scala service). Serving already computes the features, so logging them removes the training-side implementation entirely. Forfeited: iteration speed — every new feature waits a full training window in the log before it can be trained on (acceptable here by the stated monthly cadence) — plus log storage, answered by weighted sampling.

(b) **Feature store.** Shared features across models and teams are the store's defining case: one declared computation, one ingestion-time run, every consumer reads the same values on both the offline and online sides. Log-and-wait cannot serve this shape (each model's serving log captures only its own traffic and its own feature subset), and transform-in-model would bake fifty shared transforms into four artifacts — four implementations again. Forfeited: everything after the fetch stays open — post-fetch transforms still need repair 2, end-to-end certification still needs repair 1 — plus the infrastructure and the as-of join machinery the store must run.

(c) **Transform-in-model.** Crosses are instance-level and ride in the graph directly; mean–variance scaling is full-pass and rides as analyze-phase constants; one framework spans the stack, so the exported graph executes natively at serving. Because the transform ships with the weights, a new feature is trainable the day it is written — no logging horizon, which is the constraint that ruled out log-and-wait. Forfeited: an analyze pass before every training run, artifact weight, and framework lock-in — the stack can never split its service and model frameworks without losing the pattern.

A mature stack composes all three, but each of these stacks has one binding constraint, and the constraint — not preference — picks the repair.
</Solution>
</Exercise>

<Exercise>
Mixed review: <Ref lesson="data-leakage-and-splitting">the leakage lesson's</Ref> forward exercise listed what must ship beside the model weights: the fitted scaler's $\mu_{\text{train}}, \sigma_{\text{train}}$, imputation values, category vocabularies, hash bucket counts, and the transform code that applies them. Restate that answer in this lesson's vocabulary: which repair strategy is "ship the scaler with the model," and how does each listed item classify under the instance-level/full-pass distinction?

<Solution>
"Ship the scaler with the model" is repair 2, the Transform pattern: the transform logic and its fitted artifacts ride inside the exported model, so serving executes the one true implementation instead of reimplementing it against a shipped parameter list.

Classification: $\mu_{\text{train}}$ and $\sigma_{\text{train}}$ are full-pass artifacts, computed by an analyze phase over the training split and frozen into the transform graph as constants. Imputation values (a median, a mean) are full-pass artifacts with the same treatment, and category vocabularies likewise: a vocabulary is a pass over the data. Hash bucket counts and the hash itself are instance-level: <Ref lesson="features-at-scale">the hashing trick</Ref> is pure code with a config constant, needing no analyze phase, which is exactly why that lesson called it the transform that "ships as code." The application order is code too, and the transform graph itself is what carries it.

The leakage lesson's warning case (serving computes fresh statistics over live traffic) and the feature platform's config-constant fork are the two ways the same items go wrong when shipped *beside* the model instead of *inside* it: a parameter list beside the artifact invites a second implementation to consume it.
